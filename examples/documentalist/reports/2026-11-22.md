# Documentalist, 2026-11-22: import, sync and revocable sharing on a local instance

A dated record of the macOS run and a Windows follow-up. What it changed in OpenGuildKit is in [Project documentation and sharing](../../../docs/documentation.md) and in the `docs share` commands.

Instance: Documentalist at commit `947429b19da6f4e409738fd195960ae99e99c4ef` (merge of PR #24, 2026-11-11; still the head of `main` on GitHub on the day of the run), Next.js 16.4.3, built with `npm run build` and run with `npm start -- -H 127.0.0.1 -p 3000`, on Node.js v26.13.0 and npm 11.20.0 under macOS. The README recommends Node.js 22 and its CI runs on 22: this run did not use the supported version. Data in a local folder (`DOCUMENTALIST_DATA_DIR`), `DOCUMENTALIST_URL=http://127.0.0.1:3000`, `DOCUMENTALIST_COOKIE_SECURE=false`, `DOCUMENTALIST_SMTP_URL` pointing to a local SMTP sink written with the Python standard library (each message saved to a file), `DOCUMENTALIST_PRIVATE_HOSTS=127.0.0.1`. OpenGuildKit from branch `fix/field-campaign-final` at `6d61b96` (`openguildkit 0.16.1+source`), run from source. All data is synthetic; the only addresses used end in `@example.test`.

Two changes to a plain run, both outside Documentalist's code:

- Network: every Node process (build, server, browser scripts) was started with a preloaded guard that refuses any TCP connection that is not to the loopback interface and logs it. It logged four refused attempts: `registry.npmjs.org:443` once at the start of `next build`, and `api.github.com:443` (twice) and `codeload.github.com:443` during the deliberate GitHub import attempt described below. No connection left the machine. The Python helpers listened on 127.0.0.1 only.
- Fonts: the layout loads Barlow, DM Sans and IBM Plex Mono with `next/font/google`, which downloads them at build time. The build ran with `NEXT_FONT_GOOGLE_MOCKED_RESPONSES`, which serves a local system font instead. Only the typeface differs.

The administrator's actions went through the HTTP routes the interface calls, with the `Origin` header the server requires for every change. The reader used a separate browser: a fresh Playwright 1.64.1 Chromium context with its own cookies. The owner's reader settings were driven in their own Playwright context, which received the administrator's session cookie from the HTTP login: no credential was typed in a page. The local test password and session files were kept outside the repository and appear nowhere in this report.

## Issue #27: import, then sync of an updated page

OpenGuildKit's guide sent the export through "Import from GitHub" with three folders. That path could not run here.

| Step | Observed |
|---|---|
| GitHub import, local URL | `repository` set to `http://127.0.0.1:8929/example/support-portal` or to `file://` and the path of a local Git repository: 400, "Dépôt invalide. Utilisez owner/repo ou une URL github.com." |
| GitHub import, `owner/repo` | The server tried `api.github.com` and `codeload.github.com`; the guard refused both and the import failed (400, "fetch failed \| Repli zipball: fetch failed"). |
| Why there is no local path | `src/lib/github.ts`: `parseRepo` (lines 27-38) accepts only `owner/repo` or a `github.com` URL; `isAllowedGithubHost` (40-48) allows only `api.github.com`, `github.com`, `codeload.github.com` and `*.githubusercontent.com`; the DNS check (66-73) refuses any non-public address and, unlike `safeFetch` in `outbound.ts`, ignores `DOCUMENTALIST_PRIVATE_HOSTS`. There is no setting for another host, no local repository and no archive upload. |

So the import was exercised through the two paths that work without github.com.

**Local Markdown upload** ("Importer un fichier Markdown" in Outils, one file per pick, `POST /api/documents/import`), into "Support portal files":

| Step | Pages in the space |
|---|---|
| Before | 1 ("Welcome") |
| The three pages of `examples/documentalist/docs-site` (reference, learn, blog) uploaded one by one | 4. All three are in Reference, have no source path and take the file name as title. |
| The updated reference page (export 1.4.1) uploaded again | 5. A new page holds 1.4.1; the 1.4.0 copy stays. The upload is a one-time copy and duplicates. |

**GitLab import pointed at a local stand-in.** The GitLab host is configurable and `DOCUMENTALIST_PRIVATE_HOSTS` allows an internal one. A small Python stand-in answered the two GitLab API v4 routes the import calls (`repository/tree`, `repository/files/<path>/raw`) from a local Git repository. It is a test double, not GitLab. After that fetch, GitLab and GitHub run the same `importRepositoryFiles` (`src/lib/store.ts` lines 1283-1735), which matches pages by space, source path and locale (lines 1518-1541). The GitLab route has one folder and no Learn or Blog folder, so every page goes to Reference (store.ts 1316-1318).

## Issue #28: a reader's access, then its revocation

| Step | Observed |
|---|---|
| Choose the mode | Inviting while the space was public: 409, "Choisissez d'abord le mode « lien magique » dans les réglages de cet espace." Settings set to `magic_link`. |
| Invite | `POST /api/spaces/<id>/access/invites` with `reader@example.test` (and an extra `expiresAt` field, silently ignored): the sink received "Votre accès à Support portal", with a link to `/portal/access?token=…` and "Ce lien expire dans 24 heures." The owner's list then held one address. |
| Reader, no link | `/p/support-portal` shows "Portail protégé": the space name, "This portal is for invited people only" and an address field. |
| Reader opens the link | The page asks to confirm ("Ouvrir la documentation"), then opens the portal. The cookie `portal-<space id>` is HttpOnly, limited to `/p/support-portal`, and lasts 8 hours. |
| What the reader sees | **The whole space**: 11 published pages and 3 categories, including README, SUMMARY and the six OpenAPI pages, not only the reference page that was meant to be shared. |
| Reader asks for a new link | From a fresh browser, the address field: "If this address was invited, an access link has been sent." A second message arrived. While invited, the reader can get links without the owner. |
| What the owner sees | In Paramètres: the heading "Personnes autorisées par lien magique", the addresses, and a "Retirer l'accès" button per address. No date, no expiry, no page list. The activity log records `POST` and `DELETE /api/spaces/<id>/access/invites` with the time and the administrator, not the address. |
| "Retirer l'accès" | Done twice: once through the route the button calls (`DELETE`, `PortalAccessInvites.tsx` line 110), then by clicking the button in the owner's browser after a new invitation ("Accès retiré pour reader@example.test."). Each time the owner's list became empty, and afterwards the database held no reading session and no pending link. |
| Reader after revocation | With the 8-hour cookie: "Portail protégé" again. The unused second link: "Ce lien est invalide ou a expiré. Demandez-en un nouveau." A new request: the same neutral message, and no message was sent. |

What the instance grants: access to one **space** (every published page that is not hidden), per address. What it does not have: a page-level share, an end date per reader, an access duration chosen by the owner. Links last 24 hours and work once, a session lasts 8 hours, and the reader can ask for a new link at any time, so access lasts until someone presses "Retirer l'accès" (`src/lib/auth.ts` lines 302-375; `access/invites/route.ts` lines 35-37 take only `email`). Magic links need SMTP: without `DOCUMENTALIST_SMTP_URL` and `DOCUMENTALIST_EMAIL_FROM` the invite route answers 503 (lines 38-44), read in the code, not run.

## The OpenGuildKit register for the same share

| Command | Observed |
|---|---|
| `docs share add ... --portal http://127.0.0.1:3000/p/support-portal` | Refused: "Give the https address of the Documentalist portal." |
| `docs share add --deliverable docs-site/reference/request-status.md --recipient reader@example.test --until 2026-12-31 ...` | Share recorded, with the reminder "Invite the recipients in the portal's reader settings now, and remove their access on 2026-12-31." |
| `docs share add --deliverable docs-site ...` (same reader, same portal) | Accepted as a second share without a warning. |
| `docs share list` / `check` | Both `active`, exit 0. |
| `check` read on 2027-01-01 (`SOURCE_DATE_EPOCH=1798761600`) | "expired: remove the access in Documentalist", exit 1. The instance holds no date, so on that day the reader would still get in. |
| `check` after "Retirer l'accès" in the instance | Both shares still `active`: the register does not see the portal. |
| `docs share revoke` for each share | `revoked`; a second revocation of the same share was refused ("already revoked by Example Admin on 2026-11-22"). |

Where the register and the instance agree: the recipient's address and the moment the owner revoked it. Where they differ: the perimeter (a file or folder in the register, a whole space in the instance), the duration (a last day in the register, nothing in the instance), the state (the register learns about an invitation or a revocation only when the owner records it), and the unit (two register shares for one address and one space are a single access in the instance).

## Not covered by this run

- The GitHub import with its three tabs, the blog dating, the read-only imported pages and a GitHub token: they need github.com.
- A real GitLab server.
- Waiting for a link (24 hours) or a session (8 hours) to expire: the durations come from the code and the cookie's lifetime.
- Team accounts invited from `/team` with the viewer role, an instance without SMTP, the MCP server, and Node.js 22.

A separate local instance used the existing Documentalist Windows build from the checkout at [`4538575`](https://github.com/azerothl/documentalist/tree/4538575fa3c8d09089ec42bb2e68ca74d40c12b4), Next.js 16.4.3 and Node.js 22.20.0. 1. Posted to `/api/github/import` with the public repository `Sandbox-podcast/OpenGuildKit`, branch `main` ([`001f1c1`](https://github.com/Sandbox-podcast/OpenGuildKit/tree/001f1c172fb0a2c171f29e41a5b90b998540bdee)), and the `reference`, `learn` and `blog` folders below `examples/documentalist/docs-site`. Import used no GitHub token.
2. The import matched and created three pages, one in each section. Listing the space's documents returned all three IDs.
3. Forced sync through `/api/spaces/sync` reported three updates, zero additions and zero removals. A second listing returned the same three IDs and sections. The GitHub source stayed at the same revision. The changed-source test is the GitLab stand-in run above.

The Documentalist HTTP regression suite also passed its ten tests against isolated data on this workstation, including MCP and key revocation. The local runtime was stopped after the checks.
