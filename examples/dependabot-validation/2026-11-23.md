# Dependabot pagination validation, 23 November 2026

The pilot was a private, disposable repository owned by the tester. Its package manifest and lockfile held two intentionally vulnerable dependencies; the repository contained no application or production data. Dependabot alerts and the dependency graph were enabled for the pilot. Raw exports and the test project's register stayed outside OpenGuildKit because they contain private repository and advisory details.

The import run used OpenGuildKit 0.17.0 at `6ec06a5`, GitHub CLI 2.96.0, Python 3.14.0 and Node.js 24.12.0. The account that prepared the pilot had administrator access. A separate GitHub Actions run checked the API with a repository-scoped token limited to Dependabot alerts read access.

## Capture and compare

In a private working directory, with an authorized repository substituted for `OWNER/REPO`:

```sh
gh api --paginate --slurp 'repos/OWNER/REPO/dependabot/alerts?per_page=1' > dependabot-pages.json
gh api --paginate --slurp 'repos/OWNER/REPO/dependabot/alerts?per_page=100' > dependabot-bulk.json
```

Flatten each export's page arrays and compare the number and set of alert `number` values. The one-item export returned five pages and five distinct open alerts. The larger-page export contained the same five numbers. Both exports covered all states.

## Import and match

Create an isolated OpenGuildKit test project and import the paginated export:

```sh
openguildkit --project TEST_PROJECT init --answers PROFILE.json
openguildkit --project TEST_PROJECT alerts import dependabot-pages.json --json
openguildkit --project TEST_PROJECT alerts import dependabot-pages.json --json
openguildkit --project TEST_PROJECT alerts list --json
```

The first import recorded five alerts. The second recorded zero new alerts and the register still held five. A synthetic review marked one alert confirmed; importing the same export preserved that state.

For a separate test project, `npm audit --json --package-lock-only` on the original pilot lockfile reported five findings. Importing its report and then the Dependabot export produced five register entries, each linked to both scanners. The audit was run against the lockfile; the vulnerable packages were not installed.

## Fixed alerts

After updating both dependencies in the pilot lockfile, GitHub marked three alerts fixed. Importing a fresh all-states export changed those three register entries to `resolved`, including the confirmed entry; two remained open. A second dependency update addressed a newer advisory, after which GitHub marked all five fixed. A fresh import resolved the two remaining entries. The register retained all five entries as resolved.

## Read-only access

The private pilot ran a manually dispatched GitHub Actions workflow with these permissions:

```yaml
permissions:
  vulnerability-alerts: read
```

The job did not check out the repository. It passed the ephemeral `github.token` to `gh` as `GH_TOKEN`, then made the same one-item and larger-page API requests. The job log reported `VulnerabilityAlerts: read`. Both exports contained five fixed alerts over five one-item pages, and their alert numbers matched the original export. The comparison used a hash of the sorted numbers; the log printed only aggregate counts. This run validates read access with a restricted GitHub Actions identity. The earlier import and npm audit used the administrator's exports.

To repeat it, run the capture commands above inside a private workflow with the displayed permission, `GH_TOKEN: ${{ github.token }}` and the pilot repository selected. Never publish the exported JSON, register or token.
