# Recette d'installation et de migration 0.16.1 vers 0.17.0, 24 novembre 2026

Recette de l'issue #255, faite avant la publication de 0.17.0 (#254 attend l'étiquette signée du mainteneur). Elle
couvre macOS seulement et teste une construction locale de 0.17.0, pas le fichier publié de la release.

## Ce qui a été testé

| | |
|---|---|
| Système | macOS 26.6.2 (25G83), arm64 |
| Outils | Python 3.15.2, pip 26.2.2, build 1.6.1, Node.js 26.13.0, npm 11.20.0, Git |
| 0.16.1 | Fichiers publiés de la release `v0.16.1` (préversion du 20 novembre 2026, commit `a59fffc`), téléchargés avec `gh release download` |
| 0.17.0 | Construction locale du commit `a8e9df0` (branche de la PR #318 : `main` et les correctifs du troisième audit), avec les étapes de `.github/workflows/release.yml` |

Écarts avec la release : le workflow construit sur `ubuntu-latest` avec Python 3.13 et Node.js 24, et écrit les
empreintes avec `sha256sum`. Ici, macOS, Python 3.15, Node.js 26 et `shasum -a 256`. Les empreintes de la construction
locale ne seront pas celles des fichiers publiés : il faudra refaire la vérification sur ces fichiers.

## Migration sur une copie du projet 0.16.1

Mise à niveau de l'environnement 0.16.1 avec `python -m pip install --upgrade` de la roue 0.17.0, comme le dit
`docs/install.md`, puis, dans une copie du projet :

| Commande | Résultat |
|---|---|
| `check` avant `sync` | Sortie 1 : « instructions are out of date. Run openguildkit sync » |
| `task list` | Lit les deux tâches, avec leur statut |
| `integrations --host other` | Installe `.agents/skills/openguildkit/SKILL.md` (0.17.0) |
| `update` | « The project has no catalog lock yet » |
| `sync` | Réécrit `AGENTS.md`, crée `catalog.lock.json` (4 enregistrements), nomme les deux tâches consultées sous les règles précédentes |
| `host apply` | Sortie 1 : le profil 0.16.1 n'a pas d'hôte, il vaut `other` et rien n'est écrit. Après `profile set host claude-code --by … --reason …`, `host apply` écrit `.claude/settings.json` et `check` sort avec 0 |
| `update`, `check` après `sync` | « 0 records changed since the project's lock », `check` sort avec 0 |
| Fichiers des tâches | Inchangés octet pour octet par la migration (`git diff` vide sur `.openguildkit/tasks`) |

Une tâche approuvée par 0.16.1 n'a pas pu être créée ici. Le dépôt en a une : `tests/fixtures/upgrade/v0.16.1.json`,
écrite par 0.16.1 avec une approbation faite à un terminal. Ses fichiers ont été recopiés dans un dépôt Git neuf et
migrés avec la roue 0.17.0 installée :

- `check` sort avec 1 et nomme l'approbation sans sceau avec la commande `task consult request-status --reuse-answers`. `handoff`, `verify`, `export` et `complete` refusent avec le même message. `sync` nomme la tâche.
- Le fichier de la tâche approuvée reste identique (SHA-256 `9856893a…` avant et après), `task list` et `task show` le lisent.
- `task consult request-status --reuse-answers` sans terminal consulte la tâche en `unsure` et le dit. L'ancienne approbation passe dans `rounds` avec la raison de sa réouverture. `check` sort ensuite avec 0.

Décisions exportées : 0.16.1 n'avait pas `task export` ni `.openguildkit/decisions/`. Un projet 0.16.1 n'a donc pas de
décision exportée à relire ; le premier export se fait en 0.17.0, après une nouvelle approbation.

Les tests `tests.test_upgrade` couvrent le même parcours sur cette fixture et passent.

## Défauts trouvés

1. **Tâche revue sous les règles de 0.16.1 : trois messages différents.** Après la migration, `sync` disait de
   demander des modifications puis de consulter à nouveau, `task list` affichait « Waiting for the person's decision. »
   et `task consult --reuse-answers` disait que la personne approuve ou demande des modifications. Une approbation
   aurait été refusée par `task decide`. Corrigé : `task list` et `task consult` donnent maintenant le message de
   `task decide` (`stale_review_message` dans `src/openguildkit/tasks.py`). Test de non-régression :
   `tests.test_rule_changes.RuleChangeTests.test_a_review_under_earlier_rules_gives_the_same_next_step_everywhere`,
   qui échoue sans la correction. Rejoué sur une roue reconstruite avec la correction : `task list` et `task consult`
   donnent le message attendu.
2. **Note de mise à niveau incomplète.** Le changelog disait de lancer `host apply` après `sync`. Sur un projet 0.16.1
   sans hôte, `host apply` n'écrit rien et sort avec 1. Corrigé dans `CHANGELOG.md` (section « Upgrading from
   0.16.1 ») et `docs/install.md` (section « Upgrade ») : définir l'hôte d'abord, `sync` avant `check`, et la demande
   de modifications pour une tâche revue.

3. **Suite de tests du commit testé : 15 erreurs.** Sur `a8e9df0`, `PYTHONPATH=src python -m unittest discover -s tests`
   donne 1 280 tests et 15 erreurs, toutes dans `tests.e2e.test_field_kit` : le test modifie
   `fingerprint_script.ENV`, que la fusion avec `main` (#271) a retiré du kit. Le kit copie maintenant `os.environ` à
   chaque commande, donc le `PATH` que pose `openguildkit_on_path` lui parvient déjà : les trois lignes en trop sont
   retirées et les 15 tests passent.

Après les trois corrections, la suite complète passe sur macOS avec Python 3.15.2 : 1 280 tests, 3 ignorés, aucune
erreur.

Constat sans correction : une tâche encore en consultation sous les règles précédentes accepte un `task pass`. `sync`
dit de la consulter à nouveau ; si l'équipe poursuit quand même, la revue passe au statut `reviewed` et le message du
point 1 s'applique.

## Limites

- **Construction locale, pas la release.** Les fichiers 0.17.0 testés sortent d'une construction locale du commit
  `a8e9df0`. Les fichiers publiés de `v0.17.0` n'existent pas encore : téléchargement, empreinte et installation sont
  à refaire sur eux.
- **macOS seulement.** Windows et Linux n'ont pas été couverts. La CI installe la roue sur les trois systèmes à chaque
  PR, mais pas à partir des fichiers de la release.
- **Pas de contrôle exécuté par `task verify`.** L'approbation demande une personne à un terminal ; elle n'a pas été
  simulée. Le parcours s'arrête à la revue. Pour aller jusqu'au contrôle, la personne tape `task decide ID --approve`
  puis lance `task verify ID`.
- L'interface a été vérifiée par HTTP (page, script, session), pas dans un navigateur.
- Versions de Python et de Node.js différentes de celles du workflow de release (voir plus haut).

## Rejouer la recette

Sur macOS ou Linux, dans un dossier vide, avec `gh` authentifié. Remplacer `shasum -a 256` par `sha256sum` sous Linux.

```sh
# 0.16.1 publiée
gh release download v0.16.1 --repo Sandbox-podcast/OpenGuildKit --pattern 'openguildkit-0.16.1-py3-none-any.whl' --pattern 'openguildkit-0.16.1.tgz' --pattern SHA256SUMS.txt
shasum -a 256 -c SHA256SUMS.txt
python3 -m venv venv016 && venv016/bin/python -m pip install ./openguildkit-0.16.1-py3-none-any.whl
mkdir p016 && cd p016 && git init
../venv016/bin/openguildkit init --answers ../answers016.json   # name, sector, stack, components, roles, patterns, packs, boards, research, conventions, checks
../venv016/bin/openguildkit check
../venv016/bin/openguildkit task new --id add-greeting "Add a greeting function"
../venv016/bin/openguildkit task consult add-greeting --answers ../task016.json   # kind, surface, data, research, context
../venv016/bin/openguildkit task template add-greeting   # remplir, puis task review add-greeting --file REVIEW
# à un terminal, par la personne : task decide add-greeting --approve --by NOM --reason TEXTE
git add -A && git commit -m "Projet 0.16.1" && cd ..

# 0.17.0 : fichiers de la release une fois publiée (ici, construction locale avec les étapes de release.yml)
gh release download v0.17.0 --repo Sandbox-podcast/OpenGuildKit --pattern 'openguildkit-0.17.0-py3-none-any.whl' --pattern 'openguildkit-0.17.0.tgz' --pattern SHA256SUMS.txt
shasum -a 256 -c SHA256SUMS.txt
python3 -m venv venv017 && venv017/bin/python -m pip install ./openguildkit-0.17.0-py3-none-any.whl
venv017/bin/openguildkit --version
mkdir p017 && cd p017 && git init
../venv017/bin/openguildkit init --answers ../answers017.json   # ajoute personal_data, people_decisions, norms, tools, host, guard
../venv017/bin/openguildkit check
../venv017/bin/openguildkit ui --port 0 --no-browser   # ouvrir l'adresse imprimée, puis Ctrl+C
# parcours d'une tâche jusqu'à task verify ID, avec la décision tapée par la personne
cd ..
npm install --global --prefix ./npm017 ./openguildkit-0.17.0.tgz
npm017/bin/openguildkit-ci --version
npm017/bin/openguildkit-ci check-state --state ./state

# Migration, sur une copie
cp -R p016 pmig && cd pmig
../venv016/bin/python -m pip install --upgrade ../openguildkit-0.17.0-py3-none-any.whl
../venv016/bin/openguildkit --version
../venv016/bin/openguildkit integrations --host other
../venv016/bin/openguildkit sync
../venv016/bin/openguildkit update
../venv016/bin/openguildkit check
../venv016/bin/openguildkit task list
git status --short   # AGENTS.md, .openguildkit/.gitignore, catalog.lock.json, .agents/ ; tâches inchangées
```

Le test d'un dossier exFAT pour `check-state` se fait sous macOS avec une image disque :
`hdiutil create -size 20m -fs ExFAT -volname OGKEXFAT exfat.dmg`, `hdiutil attach -nobrowse -mountpoint ./mnt exfat.dmg`,
`openguildkit-ci check-state --state ./mnt/state` (sortie 2 attendue), puis `hdiutil detach ./mnt`.
