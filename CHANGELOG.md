# Changelog

What changes for a team that uses OpenGuildKit, version by version. Versions follow Semantic Versioning for the CLI; packs carry their own versions ([catalog format](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/catalog-format.md)). A release copies its section into the GitHub release notes ([release steps](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/GOVERNANCE.md#releases)).

## Unreleased

- Catalog loading: an installed package reads its packs, boards, sectors and patterns from one file, `registry/catalog.bundle.json`, validated when the wheel is built, instead of reading and validating 289 files in every process; `task list` loads the catalog and reads the lock once, and commands copy the catalog less. A checkout without the bundle reads the record files as before (#533)
- `task list`, `check` and `projects` read each task record once, not two to four times; `task list --status` and `--ready` read only the records the status index lists with a wanted status, and a closed task's line comes from the index; task records are written without indentation, 29 % lighter. 1,000 tasks: `task list` 5.8 s to 0.32 s, `check` 7.7 to 3.5 s, `projects` 10.3 to 3.7 s (#534)
- Contributing with a coding agent (#455): `AGENTS.md` and `CLAUDE.md` at the root give the commands to run, check and deliver a change in under 4 KB, `docs/agents/conventions.md` lists 29 conventions with their check and issue, and the pull request template asks what was not verified.
- RFC #446: option, off by default. A repository can follow an organization catalog: packs, patterns, brains and sectors in the format of a project catalog, read from a local Git copy at a commit a person pins with `openguildkit org-catalog set --repo PATH --commit SHA --by NAME --reason WHY` at a terminal; without `--by` and `--reason`, the command shows what the commit adds, removes and changes, with pack versions. OpenGuildKit never fetches: the commit and the fingerprint of the files read go into `catalog.lock.json`, and `check` stops with `git -C PATH fetch` or the `set` command when the copy or the commit is missing. Its records pass the checks of a project record, run no command and cannot reuse a bundled ID. The project's own records come after them; one that replaces an organization record is a warning of `check` (SARIF `catalog-org-replaced`) and a line of `org-catalog show` until a person runs `org-catalog accept COLLECTION/ID --by NAME --reason WHY`. `profile export` names the commit to pin in the other repository. A project that does not use it reads the same catalog, writes the same lock and runs no Git command ([organization catalog](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/catalog-format.md#organization-catalog)).
- One rule set aside (RFC #447): `openguildkit profile decline rule PACK/RULE --by NAME --reason WHY`, typed by the person at an interactive terminal, sets one rule aside while its pack stays in force, and `profile adopt rule PACK/RULE` restores it. The profile records who, when and why under `declined_rules`; no task consulted after it is asked the rule or checks it, `AGENTS.md` leaves it out of its pack and names it under the profile decisions with the command that restores it, and the tasks consulted before are named. An unknown rule is refused with the closest one; a required rule is refused until it leaves `required_rules`. A profile that declines no rule is unchanged: same fields, same fingerprint, same `AGENTS.md`.

The profile records who, when and why under `declined_rules`; no task consulted after it is asked the rule or checks it, `AGENTS.md` leaves it out of its pack and names it under the profile decisions with the command that restores it, and the tasks consulted before are named. - RFC #445: option, off by default. `openguildkit task new --requested-by NAME` records who asked for the work, in the task, the decision brief, the approval's seal and the exported record. A person turns `openguildkit profile set separate-requester on` on at a terminal, with `--by` and `--reason`; then `task new` needs `--requested-by`, `task decide --approve` refuses the requester as approver (compared without case or spaces, and to the signer's principal in signed projects), and `guard --ci` refuses a record approved by its requester, or a new one without a requester, when the base revision has the option on (`decision-requester-approved`, `decision-requester-missing`). A project that leaves the option off, and its existing records and sealed or signed approvals, read and verify as before. See [requester and approver](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#requester-and-approver).
- Elixir and Phoenix (#440): `detect` now reads `mix.exs`: Elixir with its `elixir:` requirement, and Phoenix with its constraint from a `{:phoenix, ...}` dependency, not from `phoenix_html` or `phoenix_pubsub` alone; the `deps` and `_build` folders next to `mix.exs` are skipped. Two new stack patterns, preselected when their stack is detected, activate two new packs, both 1.0.0: `elixir-mix` (4 rules: a committed `mix.lock` with `mix deps.get --check-locked`, `--warnings-as-errors`, `mix format --check-formatted`, `mix hex.audit`) and `phoenix` (5 rules: `protect_from_forgery` and `put_secure_browser_headers` in the browser pipeline, no user input through `raw/1`, pinned values in Ecto fragments, secrets loaded in `config/runtime.exs`), which depends on `elixir-mix`. Sources: the Elixir and Mix v1.20.5, Hex and Phoenix v1.8.17 documentation read on 26 November 2026.
- dbt and Apache Airflow (#439): `detect` now gives a dbt project the range its `require-dbt-version` declares, and recognises Apache Airflow from the `apache-airflow` package, an `apache/airflow` image or a `dags` folder whose files import `airflow`, never from the API client, a provider alone or a plain Python project. Two new stack patterns, preselected when their stack is detected, activate two new packs, both 1.0.0: `dbt` (6 rules: a bounded `require-dbt-version`, tests on primary keys, declared sources and their freshness, enforced contracts on shared models, credentials through `env_var()`) and `apache-airflow` (6 rules: idempotent tasks, light top-level code, connections and a secrets backend, a `DagBag` loader test, installs with the constraints file, removing a task). The references `dbt` and `dbt-model-contracts` now name the `dbt` pack, and the new reference `apache-airflow` names its pack. Sources: the dbt Developer Hub and the Apache Airflow 3.4.0 documentation read on 26 November 2026.
- Svelte, SvelteKit, React Native, Expo and Flutter (#438): `detect` now reads `@sveltejs/kit`, `react-native` and `expo` in `package.json`, and `pubspec.yaml` (Dart with its SDK constraint, Flutter only when a dependency names the Flutter SDK), so a React web application and a Dart package without Flutter match none of them. Five new stack patterns, preselected when their stack is detected, activate five new packs, all 1.0.0: `svelte` (4 rules: `{@html}`, `$derived` over `$effect`, `svelte-check`, accessibility warnings), `sveltekit` (4: secrets in server-only modules, server load functions, the CSRF origin check, a Content Security Policy), `react-native` (5: secrets, secure storage, deep links, HTTPS, the Upgrade Helper), `expo` (4: `EXPO_PUBLIC_` variables, `.env*.local`, the EAS Update runtime version, SDK upgrades) and `flutter` (6: `pubspec.lock`, the Flutter lints, `dart format`, secrets and obfuscation, symbol files, a current SDK). `react-native` and `flutter` add the mobile accessibility and store release packs. Sources: the Svelte, SvelteKit, React Native, Expo, Flutter and Dart documentation read on 26 November 2026.
- `openguildkit host check` adds one rule, `by instruction`, for Cursor and for GitHub Copilot when the repository holds their files: the tool reads the AGENTS.md instructions, no hook blocks an edit made through it, and `guard --ci` is the only barrier, with the hook pages and the day they were read (2026-11-26). `host scan` says the same on their line and carries the pages under `coverage.source` in `--json`, and it now also sees Copilot from `.github/hooks`. Neither became a host: read again on 2026-11-26, their hook pages still give no path of the file an edit tool is about to change, which the guard needs ([what was read](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/integrations/README.md#hooks-of-other-tools-what-was-read-and-why-none-was-added)). The exit code of `host check` does not change, and a task consultation does not record these rules (#430).
- New deliverable template `architecture-decision-record`: `openguildkit deliverable new architecture-decision-record --task ID --output docs/adr/NNNN-ID.md` writes an architecture decision record from an approved or closed decision task, filled with its status, the request, the options answered at consultation, the decision and its reason, each committee's verdict and the disagreements left open, the conditions (blockers and how each was cleared or waived) and the exported decision record with its seal. Consequences are left for the person, and `deliverable check` names them, an emptied section and the checks to tick. A task that is not a decision is refused with what to do. The only name copied is the approver's, as the decision records it. The other templates are unchanged ([architecture decision record](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/deliverables.md#architecture-decision-record), #442).
- The profile command that `openguildkit task retro --all` proposes comes with its `--reason` filled in: what comes back and the tasks behind it, as in `--reason 'task retro: rule:typescript/strict-type-checking failed in 3 tasks (a2, a3, a4)'`, one line of at most 240 characters, quoted for a POSIX shell or PowerShell. Once run, the command leaves that reason in the profile history, which keeps the link to the retrospective. `--by NAME` stays the person's to fill in and nothing is run. `--json` adds `proposed_reason` to each recurrence and keeps its other keys ([retrospective](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#the-project), #441).
- `openguildkit profile export > answers.json` prints the setup answers that give another repository this profile's patterns, packs, boards, required reviews, guard, conventions and settings, in the format of `init --questions`, for `openguildkit init --answers answers.json` there ([reuse the profile](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#reuse-the-profile-in-another-repository), #444). It writes nothing. People's names, the history of changes, the signers file, component paths, check commands and the host's tool connections stay behind, and credentials in conventions are replaced with a placeholder. A setting that names a person or lowers a protection (signed approvals, waivers, the short lane, a guard below `observe`, public research) is not carried: the export names the command the person types at a terminal in the new repository, and a declined norm comes back active until the person declines it again. `init --answers` is unchanged.
- The project MCP server (`openguildkit --project PATH mcp`) has three more read-only tools, so an agent knows where a task stands without parsing the terminal ([tools.md](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/tools.md#read-an-openguildkit-project-through-mcp), #443). `task_list` returns each task's ID, status and next open point, as `task list --json` does; `task_next` returns the command that moves a task on, never run by the server, and `needs_person: true` when it is the person's act, such as clearing a blocker or deciding; `task_blockers` returns the blockers of `task blockers --json` with their owner, what clears each one and its state. People's names, evidence, a change request's reason and a failed check's command line and output stay in the terminal. The four existing tools and their schemas are unchanged.
- New command `openguildkit projects FOLDER...`: one line per OpenGuildKit project among the folders named or their subfolders, with the guard mode, whether approvals are signed, the tasks by status, the approvals that no longer hold, the open points, the critical alerts confirmed and whether `check` passes. A folder that is not a project, or a project that cannot be read, is named and the others are listed. `--search TEXT` finds the text in task briefs, decision reasons and rule IDs and names the project of each match; `--json` gives the detail. It reads only and registers no project ([several projects at once](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#several-projects-at-once), #435).
- New command `openguildkit trace FILE`: the exported decisions whose records list the file, most recent first, each with its task, status, date, approver's initials, delivered revision, checks passed and failed, check logs changed since the export, and whether it still holds; a withdrawn or unreadable record is named as such, and a commit on the file after the last decision is named as not covered by any decision. `--json` gives the detail. It reads only ([from a file to its decisions](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#from-a-file-to-its-decisions), #434).
- The decision brief and the handoff can name the code owners of the paths a task touches, read from `.github/CODEOWNERS`, `CODEOWNERS` or `docs/CODEOWNERS` with GitHub's syntax, the last matching rule winning ([code owners](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#code-owners-of-the-touched-paths), #437). The owners are shown and never written into a task or decision record. A project without CODEOWNERS sees nothing more. `task challenge` and `task handoff` print the line.
- The answers of a task take `assumptions`, a list of sentences, for what scoping takes for granted without a confirmation ([assumptions](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#assumptions-not-confirmed), #436). `task questions --follow-ups` recalls it while the outcome or who is affected is empty; the consultation, each board pass and the handoff list them numbered; a board contests one in its entry with `contested_assumptions`; `task challenge` and the approval prompt show `Assumptions not confirmed (N)` before the request to type the task ID, the contested first. Nothing is blocked, and answers without `assumptions` read as before. At the terminal, `task consult` asks one more optional question, which Enter skips.
- Evidence changed after it was accepted shows before the closing: `task clear` records the SHA-256 of the file that clears a blocker (or of the list of a folder's files, or `external` for an https link), inside the signed payload in a project with signed approvals, and `task result` does the same for each named evidence. When such a file changes or disappears, `task blockers` and `task list` say so, `task complete` keeps it as an open point (the task closes `done-with-reservations`), and `task export` carries the state of each evidence under `evidence_states`. Until question Q2 is decided, `guard --ci` does not read it. A clearance recorded before this change reads without error and shows `no fingerprint` in `task blockers`, the only output of an existing project that changes ([evidence changed after it was accepted](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#evidence-changed-after-it-was-accepted), #433).
- A task can wait for others: `openguildkit task new "BRIEF" --after TASK` (repeated for each) records them, says the status of each, and refuses an unknown ID, the task itself or a cycle. `task list` shows what each task waits for, `--json` adds `after` and `waiting_for`, and `task list --ready` lists only the open tasks whose dependencies are done; a task whose dependency was deleted still waits. The handoff of an approved task that waits for another says first what to deliver before, without blocking. In the web interface, a task's card says how many tasks it waits for and its sheet lists them with their status. A task without `--after` is unchanged ([dependencies between tasks](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#dependencies-between-tasks), #432).
- The boards can review the diff a task delivered: after `task verify` or `task result` and before `task complete`, `openguildkit task diff-review ID` lists the files of the change and one command per board, and `task diff-review ID --board BOARD` prints that board's brief: the diff between the approved revision and the delivered one, limited to the files of the change and cut at 6 000 characters with the `git diff` command for the rest, what the decision asked (expected outcome, recommendation, verdict, blockers, disagreements left open, decision criteria) and the board's lens; `--json` for both. `task diff-review ID --submit FILE` records one board's findings, each with a file, a line, a severity (`blocking`, `important`, `minor`) and an action (`fix`, `defer`, `decision`), refuses a file with every problem at once and a `defer` on a line the change added, and says how many boards reviewed the diff and where the blocking findings are. At `task complete`, a blocking finding, a finding left to the person and a review of an earlier revision are open points (the task closes `done-with-reservations`), and `task export` carries the findings under `delivered_review`. A task whose diff no board reviewed closes and exports as before ([delivered diff review](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#delivered-diff-review), #431).
- New workflow template `integrations/github/openguildkit-retro.yml` (#429): on the first day of each month it runs `openguildkit task retro --all --json` and, only when a finding comes back, opens the issue "OpenGuildKit retrospective YYYY-MM" with each finding and the profile command a person could type. It updates the retrospective issue still open from an earlier month instead of opening another, opens none again in a month whose issue a person closed, asks for `contents: read` and `issues: write` only and writes nothing to the repository ([retrospective](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#every-month-in-ci)).
- Install a release in one line: `curl -fsSL https://github.com/Sandbox-podcast/OpenGuildKit/releases/latest/download/install.sh | sh`, or `irm .../install.ps1 | iex` in PowerShell (#428). The script downloads the wheel and `SHA256SUMS.txt` of the latest release (never a pre-release), or of the one named with `--version`, checks the wheel's SHA-256 before anything is installed, installs it with pipx or else uv, and prints four lines ending with the next commands. A hash that differs installs nothing and names the file and the release; without pipx or uv it gives the official command of each. `release.yml` attaches `install.sh` and `install.ps1` to each release with their hashes, the workflow templates keep their pinned wheel hash until the first release that ships the script, then switch to it ([install](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/install.md#install-in-one-line)).
- `openguildkit init` says, when the guard is on and approvals are not signed, that a local seal catches an accidental edit and not an agent that writes files, and gives the command that requires signed approvals (#367). The default guard stays `observe`: switching it to `enforce` is the decision #367 asks for.
- New host `gemini-cli`, the third with hooks: with it in the profile, `openguildkit host apply` declares the guard hooks in `.gemini/settings.json` (a `BeforeAgent` hook on each request and a `BeforeTool` hook on `write_file` and `replace`) and keeps the other keys of the file, and `host check` and `host scan` report them like those of Claude Code and Codex. In `enforce` the hook refuses an edit with exit code 2; in `observe` it flags the edit to the person as a `systemMessage`, since Gemini CLI documents no way to tell the agent from a `BeforeTool` hook. `init` and `sync` write `GEMINI.md`, one line that imports `AGENTS.md`, for this host only, `.gemini/settings.json` joins the files the guard protects for it, and `integrations --host gemini-cli` installs the skill in `.agents/skills/`. A project whose profile does not name the host is unchanged. The Gemini CLI pages were read on 2026-11-25 and the hook is not seen in a live session: it fails open when it cannot start, which `host check` says. Cursor, GitHub Copilot and Devin CLI document a hook that refuses a tool, but no page read shows the arguments of their edit tools, so none was added ([what was read](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/integrations/README.md#gemini-cli)).
- The short lane, opt-in and off by default, gives a change a person declares trivial a shorter way ([short lane](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#short-lane), #422). A profile that names `light_paths` (`docs/**`, `tests/**`) lets `openguildkit task new ID --lane light --paths GLOB...` open a task without the questionnaire (the lane's careful answers), with one board chosen by the paths (documentation, tests, otherwise engineering, and still the boards the profile requires) and no deliberation; the passes, the review, the blockers, the person's sealed decision, the handoff, the checks, the results, the closing and the export are the full path's. A person turns the lane on with `openguildkit profile set light-paths ... --by NAME --reason WHY` at an interactive terminal, like any setting that weakens a protection: an agent is refused, the profile records who, when and why, and a project that never turns it on behaves as before. The lane and its paths are in the seal of the approval, in the decision brief and in the exported record, and `task list` shows them. The edit hook refuses an edit outside the paths in `enforce` and flags it in `observe` unless an approved task of the full path covers it; `task complete` and `guard --ci` refuse files outside them, and `guard --ci` reads `light_paths` from the base revision, so a pull request cannot widen the lane it is judged by. A change of rules, dependencies or the profile (`.openguildkit/`, dependency manifests and lockfiles, CI workflows, `AGENTS.md`, `CLAUDE.md` and the instruction files of agents) is never in the lane. `guard --ci --format sarif` has a new rule, `decision-lane-outside`.
- The managed block of `AGENTS.md` names each rule pack with the IDs of its rules and no longer holds the text of the rules, their `Verify:` lines or the sources of the packs, which an agent reads again at every turn: the request-status example goes from 15 878 to 5 983 bytes, a seven-role monorepo from 90 541 to 16 759. The text is printed where it is needed: each board pass for the rules that concern the task, and `openguildkit task brief ID --pack PACK` for one pack in full, now with its checks, evidence and sources. The block of every project changes at its next `sync`: until you run `openguildkit sync`, `check` reports `AGENTS.md` out of date, and your own text outside the markers stays. Commit the new block with the profile.
- New packs `rust-cargo` 1.0.0 and `rust-dependencies` 1.0.0 and stack pattern `rust-cargo`, preselected for a Rust project: a committed `Cargo.lock` and `--locked` builds, RustSec advisories, the sources and licences of crates, the declared `rust-version`, lint warnings refused in CI, checked formatting, justified and bounded `unsafe`, and a service's request path that returns errors instead of panicking. `openguildkit detect` now reads `Cargo.toml`: Rust with its `rust-version`, the edition, the Axum, Actix Web, Rocket and Tokio versions, and the members of a Cargo workspace under the component of their root; `init` proposes the Cargo package name when there is no `package.json`. The reference `rust-style-guide` now names the `rust-cargo` pack.
- `openguildkit host scan` reads the instruction files and agent settings of a project (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, the agents, Skills and commands of `.claude/`, the rules of Cursor, Windsurf, Roo Code, Kilo Code and Junie, the instructions of Copilot, the MCP configurations) and reports `hidden-character` (an error: Unicode tags, bidirectional controls, zero width space; a warning for a zero width joiner outside an emoji), `instruction-override` (a warning: wording in English or French that tells an agent to drop its rules or to hide an action from the person; the block OpenGuildKit manages is not read for it) and `remote-execution` (a warning: a download piped into an interpreter, an encoded command). It works offline and read-only, needs no initialized project, prints a few lines or `--json`, and exits with 1 on an error, or on any finding with `--strict`. It blocks nothing and does not detect every injection ([what it reads and does not prove](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/host-scan.md)). (#418)
- `openguildkit host scan` also lists what could act in the repository: the agent tools whose files it holds (Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, Windsurf, Cline, Roo Code, Kilo Code, Junie, Aider, Zed, opencode, Warp, goose), each with whether the compatibility list of agents.md (read on 2026-11-25) says it reads `AGENTS.md` (an absent tool is shown as not documented as reading it) and what OpenGuildKit covers: for Claude Code and Codex what `host check` says of the hooks, for the others that no hook blocks an edit and `guard --ci` is the only barrier. - A pack rule can bound the size of a file: the `size` check takes `paths` and `max_bytes`, passes when no matching file is larger, and `task verify` names the largest file and its size ([catalog format](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/catalog-format.md#machine-checks-and-named-evidence)). ## 0.17.0

Changes since 0.16.1, the pre-release of 20 November 2026. The wheel now ships the web interface, and no command of 0.16.1 was removed.

### Install

- Install the wheel of the release with `pipx install` or `uv tool install`: both put `openguildkit` on the PATH, which the hooks of the board guard need. OpenGuildKit is not on PyPI ([install guide](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/install.md)).
- The release builds the web interface into the wheel and refuses a wheel without it. The workflow templates for the guard, the market watch and the dependency watch install the 0.17.0 wheel, checked against its hash, instead of the `main` branch.

### Setup and profile

- `openguildkit init` asks each norm that the sector, the roles and personal data imply, with the reason it is proposed, then the tools of the company, the agent host and the board guard. New projects start with the guard in `observe`. `openguildkit detect` proposes the components and versions of an existing repository, and `openguildkit preview` shows the rule packs before they are written.
- `openguildkit profile adopt`, `decline`, `add`, `remove` and `set` change the profile after setup: they record who, when and why, and rewrite `AGENTS.md`. A change that weakens a protection needs a person at a terminal.
- `.openguildkit/catalog.lock.json` pins the catalog records a project uses. `openguildkit update` shows what a newer catalog changes and `openguildkit update --apply` adopts it.
- `openguildkit host check` and `openguildkit host apply` show and install the rules the agent host can enforce, with the hooks that bring the board to the agent before every change. `openguildkit integrations` installs the agent skill and the board, market analyst and dependency watch subagents of the same version.
- `init` proposes the European Accessibility Act to e-commerce and financial services, and a `software-publisher` sector proposes ISO 27001 and the Cyber Resilience Act, each with the condition that makes it apply.
- New profile commands for the protections: `profile set approval local|signed`, `profile set waivers`, `profile set ask-every-rule`, `profile add|remove required-board|required-rule`. Only a change of rules, checks or boards voids an approval: a new tool or convention keeps them, and the commands name the approvals a change voids before writing it.
- Signed approvals are verified against the signers file as Git holds it at HEAD. An approval signed by an approver who has left since is verified against the approvers and signers file of the revision it was signed at, so it keeps holding while their new signatures are refused ([when an approver leaves](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/personal-data.md#when-an-approver-leaves)). That revision counts only once the merged branch (`origin/HEAD`, or else the upstream branch) contains it, so a key an agent commits and then reverts on a local branch approves nothing; `task list` and `check` name the signer and the revision of an approval that holds this way. [Signed approvals](https://github.com/Sandbox-podcast/OpenGuildKit/blob/main/docs/workflow.md#signed-approvals) says what the signed mode is worth in a local copy and in CI. `host apply` keeps the agent away from that file, the alert register and the project catalog. In `enforce`, `host apply` also writes `"disableAllHooks": false`, and it reports the approval rule as partial, which it is.

### Tasks

- Each brain reviews in its own pass: `openguildkit task pass` gives one brain what it needs, `task submit` records its review and refuses a malformed one with all its problems, `task progress` shows which passes are done. The brains answer each other's objections with `task deliberate` and `task respond`.
- Rule relevance: `task result --template` and `task checks` ask only the rules that concern the task, and list the others as not concerned, with the reason.
- Blockers are cleared with evidence (`task clear`) or waived within the project's policy (`task waive`) before the approval. An approval is sealed to what was approved; a project can require signed approvals (`task decision-payload`).
- Closing statuses: `task complete` closes a task as `done`, or as `done-with-reservations` with the points left open, the most serious first.
- Decision records: `task export` writes a sealed record to `.openguildkit/decisions/`, and `openguildkit guard --ci` checks in a pull request that an approved decision covers the changes.
- `openguildkit task list` lists the project's tasks with their status and next open point. `task authorize` records a person's decision on an external action outside the authorized scope.
- `task revoke ID --by NAME --reason WHY` withdraws an approval, at a terminal only; the guard stops counting it. After a rebase or a change of rules, every command gives the same reason and the same command, `task consult ID --reuse-answers`, which reopens the task under the same ID with its recorded answers, without a terminal, and keeps the passes of the boards whose brief did not change. `task list` says who took the current decision: `approved by`, `changes requested by`, `withdrawn by X (approved by Y)`, or that the approval no longer holds; `--owner` filters on that person.
- A waiver ends on its `until` day, by the real clock: after it the blocker is open again (`task blockers` shows `[waiver expired on DATE]`), `task list` names the person's options, and `task complete` and `guard --ci` refuse the task until it is resolved again. A decision, a withdrawal, a clearance, a waiver and an authorization are dated by the real clock whatever `SOURCE_DATE_EPOCH` says, so an approval's age is right; only the replayed exports follow the variable.
- A new consultation needs the `concerns` answer (`money`, `ai`, `people-decisions`, `credentials`, `none` or `unsure`). Passes, handoff and closing judge each rule with one function; each pack has a subject, so DORA, ISO 27001, the DSA notice-and-action rules and pay transparency reach the tasks they apply to. A task limited to one component runs that component's checks and consults the board of its stack.
- Lighter along the way: `task questions --follow-ups`, `task show --closing`, passes after the first of a sequence that leave out the shared instructions, a refusal that names the command the task's state allows, and commands printed with quoting a shell gives back unchanged.
- The decision prompt and `task challenge` show the check commands, advice copied between boards, and a critical alert an import resolved. Exported records list the files of the change and each blocker with how it was cleared; `guard --ci` refuses a file no record covers and fails on local approvals with `--require-signed`.

- GDPR rules for the notice to people, consent to trackers and automated decisions (Art. 22); PCI DSS and ISO 27001 requirements a development team meets first; OWASP ASVS 5.0 requirements; the dates from which the AI Act and CRA rules apply; methods for QA (test strategy) and data (definitions), and a licence policy pack. 23 rules carry a machine check, and each regulation rule a person verifies says why.

### Speed

- Commands start without the web server; the edit hook starts without the CLI and reads no catalog with the guard off; one walk of the project tree serves detection, checks and Storybook; `check` reads each task once; routing compiles each trigger once.

### Third audit

- `guard --ci` refuses a decision record placed below `.openguildkit/decisions/`, an approval whose revision the pull request does not contain, and a record that carries a withdrawal: after `task revoke`, `task export` writes the withdrawal into the record. `task export` names the new files Git does not track yet; the README closes with commit, export, then commit of the record.
- Signed approvals: an earlier revision's signers count only when the merged branch contains that revision. Waivers expire on their last day (real clock), people's decisions are dated on the real clock, and `task consult ID --reuse-answers` reopens a task without a terminal.
- `openguildkit ui` serves the page on a host name drawn for each run (`ogk-….localhost`), so its key never reaches another local server. The detector recognizes more passwords and tokens, and the page refuses more credential files.
- `init --answers` needs `personal_data`; `market checked` is refused under `local-only`; with `openguildkit` off the PATH, `host apply` says so and exits non-zero.
- The page records named evidence with who provided it, marks required evidence and rules not asked correctly, speaks French in the framing questions, and `task complete` asks the person to confirm data protection, security or AI rules set aside.
- `task result` flags one evidence cited for passed rules of three packs or more; `task verify` counts the rules to report instead of listing them; working files go in `.openguildkit/work/` (run `openguildkit sync`). French routing no longer sends "le client paie" to HR, and Stripe Elements packages are detected.
- The catalog and lock caches compare file contents; the dependency watch scans in a read-only job; CI runs four macOS jobs instead of nine.

### Upgrading from 0.16.1

- Run `openguildkit sync`: it writes `.openguildkit/catalog.lock.json`, which 0.16.1 did not have, and names the tasks consulted under the earlier rules. A task reviewed but not decided waits for the person to request changes (`openguildkit task decide ID --request-changes`), then it is consulted again.
- A 0.16.1 profile has no agent host, so it counts as `other` and `host apply` writes nothing and exits 1. For Claude Code or Codex, set the host first (`openguildkit profile set host claude-code --by NAME --reason WHY`, or `codex`), then run `openguildkit host apply` (new deny rules and hook setting).
- Approvals recorded by 0.16.1 have no seal, so none of them holds any more: until each approved task that is not completed is consulted again, `check` exits 1 on it, and `handoff`, `verify`, `export` and `complete` refuse it. `sync` names them. Consult each again with `openguildkit task consult ID --reuse-answers` (or open a linked task with `--follows`): every board reviews again, since an approval without a seal keeps no pass, and the person approves again. Their answers predate the `concerns` question: it is asked at a terminal, and without one the task is consulted as `unsure` unless `--answers FILE` gives it. A completed task keeps its record as history.
- Signed approvals need the project and its signers file committed in Git.
- Answer files of a new consultation need `concerns`, and setup answers for e-commerce or financial services answer the European Accessibility Act norm.
